## Implementation status

- The local `codex/first-customer-readiness` branch is based on GitHub `main` at `27b3442a`. The implementation has platform migrations through V31 and tenant migrations through V79.
- NVD, EUVD, JVN, GHSA, and CSAF resume from committed feed checkpoints. Capped or partly failed CSAF scopes remain ineligible for publication. The incremental finding queue, dirty rollups, and targeted publication are available for canary qualification with their rollout settings off by default.
- SSM collects up to four hosts at a time and applies only completed host captures. Failed or stale captures preserve prior evidence. SCCM streams into tenant PostgreSQL staging for tenants using incremental inventory correlation. An interrupted query restarts collection before sealing. After sealing, each committed host merge advances the durable result, and a replacement worker resumes with the remaining hosts. The candidate limits SCCM to 1,000,000 install rows and 512 MiB of serialized input per run. These are implementation limits to verify against the pilot workload.

## Customer rollout and enterprise capacity

- **First customer.** Confirm offered connectors, asset count, software density, refresh spikes, AI scope and freshness. Validate the combined candidate in one budgeted AWS qualification with representative traffic, backup and restore, tenant isolation, and rollout connection headroom. Keep the existing Standard release gates. Enforce a maximum **10-second correlation write transaction**, **p95 under five minutes** to normalized inventory and **p95 under 15 minutes** to updated findings. Measure source collection and review separately. For sizing, start with a proposed **20% resource reserve**. On the checked-in Standard shape, the worker must peak at or below **3.2 GiB** of task memory and RDS must peak at or below **80 GiB** of used storage, including staging, release history and WAL, with the agreed retention projected. If a limit is breached, reduce work or qualify a larger shape and its measured cost. Onboard in waves using the smallest configuration that passes. [Worker shape](https://github.com/AxC-SG/SG/blob/27b3442a2fcc42a3ccf331ad3d93ce9901a48d05/prototype-app/infrastructure/terraform/standard/runtime.tf#L84) · [Database allocation](https://github.com/AxC-SG/SG/blob/27b3442a2fcc42a3ccf331ad3d93ce9901a48d05/prototype-app/infrastructure/terraform/standard/data.tf#L67)
- **Enterprise target.** Qualify 100,000 assets and 50 million software observations before committing to that capacity. The proposed objective is eight hours from staged data to visible findings. Use production-shaped data, concurrent users, a change burst and a high-fan-out advisory. If the first customer needs enterprise volume on day one, run this test before onboarding. Evaluate reuse of matching results across equivalent installs with parity tests. Use measured bottlenecks to decide when to add capacity, SQS, partitioning, or a versioned read model for larger intelligence releases.
