# Review of the additional ScoutGrid AWS migration plan

**Reviewed:** October 17, 2026. **Source revision:** `bd8ecf60cf21cbc56ed7de29fa23237e04d89bbc`, unchanged since the first review. **Input:** [pasted plan](</Users/gowrikarthik.gadela/.codex/attachments/a2099ccd-e465-406b-8526-ecd2c017f3b6/Pasted text.txt>). This is a source/document review, not a deployed-environment audit or exploit test.

## Assessment

Adopt this as a useful supplement to the earlier review, with corrections before implementation. It identifies several concrete gaps the first review did not call out individually, especially tenant-unscoped sync-run lookups, stale-token restoration of a revoked platform-owner role, raw invitation/GitHub tokens, feed checkpointing, and public-schema runtime grants. Its overall ECS/RDS/S3/managed-identity direction is consistent with the existing recommendation.

Its strongest weakness is that it mixes verified code behavior, inferred exploit impact, architecture preferences, and unconfirmed customer requirements. It also puts some essential durability work after launch, changes health checks in the wrong direction, and promises regional recovery before all regional dependencies are covered.

The earlier documents remain the dated baseline: [architecture recommendation](</Users/gowrikarthik.gadela/Desktop/AI Projects/NoScan/prototype-app/docs/AWS_production-architecture-review.md>) and [70-task register](</Users/gowrikarthik.gadela/Desktop/AI Projects/NoScan/prototype-app/docs/AWS_production-migration-backlog.md>). This addendum maps changes to their task IDs and distinguishes additions from changes to the earlier proposed scope. It does not change any deployed service.

## 1. Correct the stated requirements

The second plan says the founder supplied 10–50 mid-market tenants, SOC 2 Type II, an AWS-skilled team, 99.9% uptime, and a 15-minute/4-hour RPO/RTO. Those are **not confirmed inputs in this chat**. Unless confirmed in another conversation, label them as proposed assumptions.

The confirmed inputs here are: backend and PostgreSQL on Render, frontend on Vercel, production can start with a fresh DB, and the founder delegated unknown scale/security/integration decisions to expert judgment. The earlier 5–10 design-partner target and recovery/availability objectives were explicitly proposals. This distinction matters because the second plan makes an expanded compliance and regional-DR program part of the launch budget and critical path.

Start with a bounded shared-SaaS design-partner launch. Build secure identity, tenant isolation, durable jobs, recovery, and operating evidence now. Start corporate security controls now, too. Buy a particular compliance platform/audit package, customer-specific SSO/SCIM, private collector, or regional SLA against a concrete commercial requirement and a priced implementation plan.

## 3. Recommendations to correct before execution

| Plan claim or action | Correction |
| --- | --- |
| "All 46 scheduled jobs lack cross-instance locks" | The 46 annotation count is reproducible, but the universal coordination claim is false: SKIP LOCKED/leases exist and GitHub source claims use a pessimistic row lock. Inventory each scheduler's trigger, claim, ownership/recovery, and effect semantics. Add locks only where needed; a scheduler lock alone does not make a crashed/expired job safe. |
| "Three blockers exist only because of AWS" | Tenant authorization, role re-grant, accepted-work loss, and stale schema/readiness behavior are application/multi-instance problems. They also matter on paid Render and during ordinary restarts. AWS exposes or increases the consequences; it is not the sole cause. |
| "Role ARNs aren't checked; a tenant can reach another customer's account" | AI AWS connector already validates ARN format and ARN/account binding; generic AWS targets need stronger validation. Cross-account access additionally depends on deployed task permissions and customer trust policies, which were not audited. Fix optional role/default identity and external-ID binding, but do not present a proven cross-customer exploit. Generic EC2-only credentials can fail on Fargate rather than automatically become task credentials. |
| "Encrypt every ExternalId" | AWS does not treat ExternalId as a secret. Unique server-controlled tenant/account binding and a correct customer trust policy are the important controls. AI connector already encrypts it; generic paths differ. [AWS third-party access guidance](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_common-scenarios_third-party.html). |
| "Every migration takes down the fleet" | There is a real exact tenant-target/readiness coupling. Platform migration versions are independent; not every deployment/platform-only migration causes this effect. Use expand/contract compatibility plus isolated tenant eligibility, verified against old/new binaries. |
| C6/E4: ALB checks liveness | **Change this.** ALB should use instance readiness including indispensable serving dependencies. Container/process liveness should remain distinct so a shared DB outage does not cause restart storms. Keep management access restricted and tenant failures isolated. Health checks also do not replace app fail-closed behavior; ALB can fail open if every target is unhealthy. [ALB health behavior](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/target-group-health-checks.html). |
| C15: durable accepted work and large-import changes are P1 | **Promote durability to P0** for offered async operations. One worker does not fix lost in-memory dispatch on API restart. For synchronous imports, either implement persistent async processing or explicitly cap and qualify a smaller supported workload before launch. |
| C18: shared provider budgets only matter with multiple workers | API paths can still make calls, and multiple API instances already multiply local limits. Budget the full fleet from launch; a deliberately single provider-calling worker is only a valid interim control after all callers are isolated. |
| C19: remove foreign keys at 100 tenants | Do not adopt a numeric trigger without benchmarks. The FK count/catalog/DDL-lock concern is real, but RLS does not replace referential integrity. Review measured provisioning/deletion/lock/catalog behavior and alternative placement before schema redesign. |
| D2: existing CSRF protection automatically covers cookie sessions | Cookie auth is new work. Current security is STATELESS and bypasses CSRF based on the presence of selected headers. Define session authentication, secure cookie scope, CSRF protection, login/logout behavior, session rotation/fixation, OIDC state/nonce/PKCE, and server-side expiry/revocation together. A dummy Authorization header must not bypass cookie-session CSRF. |
| D4: a second Cognito app client isolates staff | A client split is helpful organization, not sufficient authorization. Enforce intended client/issuer/token type and server-side staff access. Define whether same-pool SSO is acceptable or a separate pool/IdP trust boundary is required. |
| A4: old Terraform used public tasks and public S3 website | The cited historical stack places ECS tasks in private subnets with public IPs disabled; its archive bucket is private/KMS/versioned; frontend used ECS. The attachment misdescribes those parts. Its owner DB credentials/API-key wiring and missing current deploy boundaries are the reasons not to restore it unchanged. |
| E5: SSM DB forwarding logs SQL; C14: read-only app root | SSM tunnel/session metadata is auditable, but port-forwarded SQL payload is not session-content logged. Configure DB audit policy and individual admin credentials if needed. ECS Exec also requires a writable filesystem; a separate temporary restricted admin task is preferable to weakening immutable application containers. [SSM logging limitation](https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager-logging.html), [ECS Exec constraints](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ecs-exec.html). |
| E12: Bedrock keeps data "inside your AWS boundary" | Bedrock is an AWS-managed service, not proof that customer payloads remain in your VPC/account or chosen region. Specify model, retention, logging, endpoint/network policy, and inference profile; cross-region profiles route outside the source region. Migration is a policy/quality/cost choice, not a privacy shortcut. ## 4. CloudFront alternative: valid, with conditions

The CloudFront proposal is real and merits consideration. AWS currently lists Pro at **$15/distribution/month**, including specified WAF/DNS/logging benefits. Business is **$200**, with private origins and listed SLA coverage that Pro lacks. Route 53 inclusion requires an attached qualifying hosted zone. Usage allowances and plan features must be checked against the chosen configuration. This is an update the earlier cost discussion should include as an alternative. [AWS CloudFront plans](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/flat-rate-pricing-plan.html), [pricing](https://aws.amazon.com/cloudfront/pricing/).

A single **browser origin with two upstream origins** can simplify browser API/session behavior. It still needs implementation and verification:

- Use private S3/OAC for SPA assets and a restricted ALB origin. Origin IP restrictions alone admit other CloudFront distributions; add an enforced distribution-specific mechanism/header, redact it from logs, and rotate it.
- Disable authenticated API caching; forward required query strings, methods, cookies and auth/CSRF headers. Preserve API 401/403/404/5xx responses and define safe error caching.
- Implement SPA deep-link fallback only on appropriate UI behavior. Never turn every distribution-wide 403/404 into a 200 `index.html`, which would corrupt API failures and missing-JS errors.
- Retain CSP destinations for chosen Sentry, Turnstile, identity and signed S3 uploads. `connect-src 'self'` alone is incompatible with retained third-party browser calls. Direct S3 upload still needs bucket CORS.
- The managed core WAF `SizeRestrictions_BODY` rule really does block bodies over 8 KiB; do not confuse that rule with CloudFront's larger inspection allowance. Prefer direct bounded S3 uploads; otherwise scope/test upload exceptions rather than disabling inspection globally. [AWS managed rules](https://docs.aws.amazon.com/waf/latest/developerguide/aws-managed-rule-groups-baseline.html).

I would keep Vercel during the core migration to limit simultaneous change. CloudFront can be chosen as a separate frontend/edge workstream if one browser origin, provider consolidation, and its tested plan/contract are worth the added work. Saving one Vercel seat or reducing one vendor alone does not justify making frontend migration a launch blocker. A provider SLA is also distinct from ScoutGrid's own measured availability and customer contract.

## 5. Disaster recovery and compliance need separate commitments

Regional DR is a useful expansion of the first plan, but E13 is P1 while H3 is P0 and permits a drill after GA. Resolve that contradiction. If the sold RPO/RTO includes complete region loss, the entire DR dependency chain and measured regional drill must precede that promise. Otherwise label initial targets as same-region recovery and phase regional capability separately.

Recover identity and sessions, email sending readiness, IAM/KMS permissions, image/IaC/state access, DB parameters/network/grants, object-reference consistency, destination quotas, customer allowlisted egress IPs, certificates/origin/DNS, monitoring and failback—not just RDS and S3. Native RDS cross-region backup replication is supported for Multi-AZ DB instances, not Multi-AZ DB clusters; replicated latest-restorable time and object lag must be measured. [RDS replication limits](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_ReplicateBackups.html).

**Current Cognito does offer multi-region replication**, with prerequisites and added pricing. Its current documentation excludes TOTP MFA from secondary replicas. The plan's authenticator-app MFA therefore needs an explicitly tested regional authentication strategy. Do not assume that replicating DB/secrets makes login recoverable. [Cognito regional replication](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-multi-region.html). Current Cognito also supports passkeys satisfying MFA when configured for user verification; do not reject that option based on older product limitations. [Cognito authentication flows](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-authentication-flow-methods.html).

Define recovery by threat scenario: AZ outage, region outage, accidental logical deletion, and privileged account compromise are different. A monthly immutable cross-account copy can lose nearly a month for the last scenario; it does not establish a 15-minute immutable/off-account RPO. Vault Lock and audit Object Lock retention should be selected carefully with deletion/retention policy, costs, and key recovery—not enabled with an arbitrary universal retention period.

For SOC 2, retain corporate MFA, managed devices, access reviews, change evidence, incident response, vendor oversight, recovery tests, and independent testing. Do not treat a particular compliance vendor, one-year storage for every log, every cloud finding being green, or four accounts as a universal SOC 2 requirement. The control design and evidence must match the scoped service and commitments.

A Type I before Type II is an optional path, not an automatic prerequisite. A three-month observation period and report five to six months after GA are not guaranteed; agree the period, readiness and audit/reporting schedule with the chosen auditor. SOC 2 is an attestation/report, not an automatic cloud-platform certification. The proposed $30–50k is an unquoted budget hypothesis and excludes internal time unless explicitly budgeted. [Auditor explanation of reporting periods](https://www.schellman.com/services/soc-compliance-and-attestations), [direct Type II/readiness options](https://www.schellman.com/blog/soc-examinations/what-to-expect-soc-2-readiness).

## 6. Reconcile cost, scope, and timeline

The second plan's arithmetic is coherent: $655 production + $135–235 staging + $27–67 SaaS = **$817–957/month**, rounded to $850–1,000. That is a different scope from the earlier **$375–650 production baseline**, which excluded staging, AI consumption, engineering and audit work, used a smaller starting database, and deferred full regional DR. The two totals are not directly competing quotes.

Do not call the larger estimate "everything." Add explicit assumptions/allowances for variable AI, cross-region object/backup transfer/storage, regional identity/session/email recovery, security/log volume and immutable retention, support plans, corporate identity/MDM, audit tooling/auditor/penetration testing, and engineering/on-call labor. Quote actual Oregon RDS class/deployment/storage, rather than treating a third-party instance lookup as a purchased configuration. Credits are conditional and temporary; design sustainable uncredited unit economics.

Use a two-scenario budget: (1) bounded design-partner production with essential security and demonstrated same-region recovery; (2) expanded enterprise operations with larger DB, full regional DR and a scoped SOC 2 program. The second plan is a plausible starting envelope for scenario 2, subject to correcting omitted dependencies. Keep exact instance sizes and 2→6 API replicas as experiment values constrained by DB/provider budgets, not capacity guarantees.

The proposed load test is much larger than it first sounds: 10 tenants × 10,000 assets × 200 components = **20 million asset-component associations**, plus potentially 10 million for the 50,000-asset tenant, before shared intelligence/history. Distinguish installations, normalized identities, per-BOM components and finding/correlation rows. That workload needs a separate measured stress tier and can invalidate the proposed database cost.

Stopping staging compute does not stop ALB/NAT/storage/backup charges. A one-NAT lean topology adds an AZ egress dependency and possible cross-AZ charges, not just a database CPU-credit risk. Savings commitments should follow stable measured base load and a current quote, not a promised $100 saving. AWS Activate eligibility/amounts have evolving tiers; use the current application offer and record approval/expiry. [Current Activate offers](https://aws.amazon.com/startups/credits).

The 12–14 weeks with three engineers is a plausible planning hypothesis for the expanded scope, not a validated estimate. Likewise the earlier 8–12 weeks with two engineers plus part-time help was conditional on a smaller launch. Re-estimate from identity/session, queue/lease, connector and recovery spikes. The week-nine pilot shortcut must include coherent production identity, tenant authorization, durable work, meaningful monitoring, backup/restore and an operator; it cannot omit D/G/H simply because B/C/E/F are complete.
